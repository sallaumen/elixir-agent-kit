# Concepts audit: what changes a decision?

Baseline: Git release v1.2.1, commit `858d1522700495b5b916399633074b39230dc0ae`.
Three independent reviewers examined functional refactoring, architecture and
readability. Each proposed a narrow change, prepared an original case and an
inverse, and fixed the criteria before collecting answers. All evidence is
synthetic. Model trials used fresh, tool-disabled Codex sessions (GPT-6.1-Sol,
medium reasoning); no participant saw another answer or the scoring key.
Comparisons use the selected baseline guide versus a candidate, not unguided
versus guided. Each pair saw identical case material. Scripted assertions were
run by the evaluator, separately from the model.

The architecture rubric required two independent gains on ownership and
normalization with no unnecessary structures in the controls. A blinded judging
session per case scored shuffled answers: baseline 2/5 twice versus candidate
5/5 and 4/5; controls 4/4 throughout. The 4/5 answer omitted a concrete
policy-only cutoff example. The [submitted reviews and grades](../fixtures/concept-review/architecture/reviews.json)
retain the disagreement in recommendations and the limits of the score.

The final functional wording differs from the A/B candidate: it also separates
functions from data and clarifies that a forwarding wrapper adds no decision.
Two further fresh sessions received the final guide and the original frozen
cases. Both passed 4/4 hidden checks, supplied setup-free pure-rule tests, and
caught the timing mutation; the inverse implementation remained unchanged.
This confirms compatibility on reused cases, not a new independent effect.
Final guide SHA-256: functional `79039fdc42850e87c3c787212b6b6d75ac2f00f5e207c16a868f7e05d0f45eb9`;
architecture `690ab5d1167819ee101b01679106b3f404a20a531edb96431c44822d4d6d5eab`.

**Independent transfer.** A separate maintainer supplied a new result-side
example: the policy returned dashboard colors which a digest interpreted as a
review decision. One fresh execution per arm, unchanged candidate, same shared
brief. Both separated the editorial decision from the output formats, kept
public outputs and proposed changing only dashboard colors as the check.
This was a tie; the original advantage did not recur on the clearer case.
This pair was assessed directly, not by a blinded judge.

**Routing and catalog.** Four more sessions saw the existing catalog, routing
guide and contract, without any supplied workflow. Separate neutral requests
selected architecture-review for cross-context vocabulary, functional-refactoring
for hidden inputs across two exports, readable-code for private clause precedence
and NONE for an explicitly specified comment typo called “clean code.”
These are text-only routing probes, not installed-client discovery tests.
Keep 38 workflows. A context that already exposes domain values needs no new
behaviour, DTO, process or umbrella; a private name does not justify a public
API migration. Existing module-design and abstraction-layers own those adjacent
decisions.

**Evaluation tooling.** Passing the same historical TSV twice used to turn two
readable-code runs into four successes. The CLI and committed-result checks now
reject repeated execution identities (client, model, kit revision, run ID);
two independent runs with distinct IDs remain countable. This guards against
duplicate records, not fabricated transcripts or reuse under different IDs.

See the [offline counterexamples](../fixtures/concept-review/README.md) for
the runnable probes. They demonstrate the contracts; rerunning them cannot
recreate a model review. None ships with the library. The synthetic cases
establish neither production impact nor correctness across other models or the
rest of the catalog. This is not a Hex publication.
